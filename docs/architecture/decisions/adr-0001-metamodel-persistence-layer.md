# Introduce a persistence layer for the strategic-architecture metamodel

## Context and Problem Statement

The homemade-claude-kit metamodel produces artefacts across five layers:

| Layer | Artefacts | IDs minted |
|---|---|---|
| Business architecture | personas, competitive landscape, lean canvas, capability map, value streams, objectives, quantitative models | P-NN, BC-NN, VS-N.M, OBJ-NN, KR-NN.M |
| Domain | bounded contexts, glossary terms, domain model (entities, aggregates, events) | BC-NN, GT-NN |
| Product | FBS (functionalities), delivery roadmap (epics), PRDs, quality attributes | C-N.M.FXX, E-NN |
| Quality assurance | (planned) test plans, test cases, bug reports | (none yet) |
| Operations | runbooks, RCAs, incidents | (none yet) |

Today every artefact is a markdown file. Cross-references between artefacts use text-based ID conventions (e.g. `C-N.M.FXX`, `E-NN`) that are:

- **unenforced**: no tool validates that a referenced ID exists
- **unqueryable**: answering "which functionalities belong to a given epic and their total estimated effort?" requires reading and mentally joining multiple files
- **drift-prone**: renaming or re-numbering an ID in one file does not propagate
- **computation-hostile**: cross-artefact aggregation (effort estimates, roadmap timelines, model inputs) requires fragile markdown parsing

A deeper problem surfaces when AI agents (Claude, Codex) are the primary authors of metamodel artefacts: **LLM output is non-deterministic**. IDs generated by an LLM have no collision guarantee, no referential integrity check, and can silently drift across sessions. Two runs of the same skill on the same inputs may produce different ID strings.

The desired workflow is: the agent *converses* to think through an artefact, then *calls a tool* to persist the structured record. The tool generates the ID deterministically from a DB sequence and returns it. The agent then uses that ID in markdown prose. The conversation stays natural; the structure is enforced by the tool layer, not by the agent's memory.

## Decision Drivers

- Must cover all five metamodel layers: a tool that handles product but not business architecture solves only part of the problem
- Must enforce ID relationships (FK semantics between artefact types)
- Must enable cross-artefact queries (e.g. effort per epic, KRs per objective)
- IDs must be generated deterministically by the persistence layer, never by an LLM
- Must be usable by AI agents (Claude, Codex) as a deterministic tool layer
- Must be Python-native to integrate with marimo as the analysis interface
- Must work for a solo founder / AI-only MVP with zero infrastructure overhead
- Must not lock data in a proprietary cloud service
- Schema must be evolvable as new artefact types are added (QA, ops layers pending)
- Upgrade path to multi-user / HTTP API must be clean without rewriting the core

## Considered Options

- **A.** Status quo: markdown files with text ID conventions
- **B.** SaaS project-management tools (Linear, Jira/Confluence, Notion)
- **C.** OSS self-hosted tools (Plane, AppFlowy, Anytype)
- **D.** Local DuckDB file, human-edited via marimo
- **E.** Structured YAML source files + DuckDB materialized query layer
- **F.** Local MCP server exposing CRUD tools over DuckDB, with YAML export for git
- **G.** CLI tool (adr-tools style) over DuckDB, with YAML export for git
- **H.** Graph database (Neo4j / property graph) over the artefact FK graph, with YAML export for git
- **I.** CLI tool (adr-tools style) over **SQLite** (stdlib), with YAML export for git

## Decision Outcome

Chosen option: **I (CLI tool + SQLite + YAML export)**, because clew's workload is OLTP-shaped at small scale and SQLite delivers the same agent-as-primary-user contract as option G with one fewer runtime dependency and a simpler concurrency story.

Claude Code already has the Bash tool. A CLI *is* the tool layer: no server process, no protocol, no JSON-RPC. The agent calls `clew new persona ...` via Bash and receives a deterministic ID back. The application layer generates all business IDs from an `id_sequences` table (never by the DB engine and never by an LLM). Markdown narrative written by the agent references those IDs. `clew export` produces a git-readable YAML snapshot.

The design is deliberately modelled on `adr-tools`: a small, composable CLI that does one thing well per command, installable in one line, usable in scripts and agent sessions alike.

```
AGENT (Claude / Codex)
  ├── converses to think through content
  ├── calls CLI via Bash to persist structured records
  │     clew new persona "Ophthalmologist" --role "..." → P-01
  │     clew new functionality "Schedule surgery" --cap C-N.M → C-N.M.FXX
  │     clew set complexity C-N.M.FXX M
  │     clew link C-N.M.FXX E-NN
  │     clew impact C-N.M.FXX → { affected: [E-NN, PRD-0007, VS-1.3, …] }
  └── writes markdown prose referencing returned IDs

CLEW CLI (Typer, installed via uvx / pip)
  ├── CRUD commands per entity type
  ├── Business ID generation from id_sequences (never by the agent)
  ├── FK enforcement at write time
  └── clew export → snapshot/

SQLITE (local .db file per project; stdlib sqlite3)
  ├── Schema for all five metamodel layers
  ├── FK constraints enforced (PRAGMA foreign_keys = ON)
  ├── WAL mode for safe concurrent readers + serial writer
  └── Single source of truth

MARIMO NOTEBOOKS (read-only analysis)
  ├── Effort estimates + rollup to epics
  ├── Roadmap / Gantt
  └── KR coverage, financial models
  └── Reads via pandas.read_sql / Polars

MARKDOWN DOCS (narrative layer)
  ├── Written by agent, referencing CLI-returned IDs
  ├── Research URLs, decisions, context
  └── Rich prose that structured data cannot express

snapshot/ (YAML export, git-tracked)
  ├── Generated by `clew export`
  ├── Human-readable; never edited directly
  └── Deterministic: same DB state always produces same YAML
```

**SQLite chosen over DuckDB (option G rejected).** clew's write path is single-row INSERTs per CLI command (OLTP shape); its read path is a mix of point lookups, FK resolution, and recursive-CTE traversals at hundreds-to-low-thousands of rows per project. Both engines answer in microseconds at this scale, so DuckDB's columnar advantage on analytical scans never engages. SQLite wins on three concrete axes:

1. **Stdlib-shipping** (`import sqlite3`) eliminates one pip dependency and one binary wheel from `pip install clew`.
2. **OLTP-native row store** is the natural fit for CRUD on single artefacts; DuckDB's column store carries per-write overhead with no offsetting read-side benefit at this scale.
3. **WAL mode** handles the single-writer-per-repo constraint cleanly via the engine's own locking, replacing the `flock` wrapper that option G required.

The trade-off accepted: SQLite has no equivalent to the DuckPGQ property-graph extension and no in-tree vector-search story. Both were v2 "nice to know exists" options for option G, not load-bearing capabilities. Recursive CTEs cover the ≤5-hop traversal that the metamodel actually performs (see option H rejection below), and vector search is deferred to a v2 add-on (`sqlite-vec`) only if/when artefact volume warrants similarity queries.

**Graph database rejected (option H).** The metamodel has 19 artefact types with a fixed, typed schema and bounded FK traversal depth (≤ 5 hops: persona → value stream → FBS functionality → epic → PRD). Relational SQL with recursive CTEs covers all required graph-style queries without a graph engine, server process, or JVM dependency. The "semantic layer" benefit cited in Neo4j literature is a query-composition concern (helping agents write better queries) addressable at the CLI layer, not a storage-tier concern. See §H in Pros and Cons for full analysis.

**Semantic / vector search deferred to v2.** At MVP scale the query problem is exact-ID reference resolution (a reference problem), not fuzzy similarity retrieval (a retrieval problem). If similarity search becomes load-bearing later, `sqlite-vec` is the designated in-engine add-on; no separate vector database is required for v1 or v2.

### Positive Consequences

- Business IDs are application-generated from an `id_sequences` table: deterministic, collision-free, never LLM-generated
- FK violations fail at command time; the agent receives a clear error message
- Any agent with shell access (Claude Code, Codex, scripts) uses the same CLI
- No server process: the CLI is stateless; invoked per command, exits cleanly
- Installable in one line: `uvx clew` or `pip install clew`
- Composable: pipe, script, combine with other shell tools
- Markdown narrative survives unchanged: agents write prose; CLI manages structure
- YAML export is deterministic (generated from DB state, not by an LLM)
- Analysis notebooks are pure read-only consumers, cannot corrupt data
- Zero non-stdlib dependency for the DB driver itself; `pip install clew` does not pull a separate DB binary wheel
- Upgrade path is clean: wrap the same `crud.py` core in an MCP server or FastAPI when a dedicated protocol or multi-user access is needed; no core layer rewrite

### Negative Consequences

- Schema design and migration discipline required as the metamodel evolves
- Existing markdown artefacts with hand-written IDs must be migrated: one-time cost per project
- `clew` package must be developed and maintained
- No in-engine property-graph or vector-search extension (DuckPGQ / VSS); if/when needed, `sqlite-vec` is the in-engine add-on for similarity search and graph traversal stays in recursive CTEs

### Concurrency model

clew v1 is **single-writer per repository**. This is a deliberate scope decision, not an oversight:

- SQLite is opened in **WAL mode** (`PRAGMA journal_mode = WAL`). Concurrent readers proceed without blocking; concurrent writers are serialised by the engine's own busy-handler with a bounded timeout. The second writer waits rather than racing; no data is lost.
- `PRAGMA foreign_keys = ON` is set per connection (SQLite default is OFF for legacy reasons; clew enforces FKs always).
- YAML snapshot files are written via temp file + atomic `rename(2)` to eliminate partial-write windows.
- On startup, the CLI reconciles DB-vs-YAML drift: if the DB is ahead of the YAML (which can happen if a process crashes between DB commit and YAML rename), the YAML is regenerated from the DB. This makes the dual-write self-healing without requiring a true distributed transaction.

Cross-machine concurrency (two humans editing the same metamodel from different checkouts, CI writing while a human writes, or a web UI operating alongside the CLI) is **explicitly out of scope** for v1 and v2. That use case requires a real database server with its own concurrency control and conflict resolution, which is the v3 target. Bolting distributed coordination onto a local-file CLI is not attempted.

### Upgrade path

```
MVP    CLI (Bash tool in Claude Code / Codex) → SQLite (WAL mode)
v2     MCP server wrapping the same crud.py core → dedicated MCP clients
       (+ sqlite-vec as an optional in-engine extension if and only if similarity
         search becomes load-bearing — not committed; recursive CTEs cover v2's
         actual query needs)
v3     FastAPI + Postgres wrapping the same crud.py core → HTTP / multi-user / mobile
```

The `crud.py` core never changes between versions. Only the interface layer grows. The jump from v2 → v3 is the one that lifts the single-writer constraint; v1 → v2 is a transport change, not a concurrency change. The v2 → v3 swap from SQLite to Postgres is the natural path: both are relational, both speak similar SQL, and the application-layer ID generation (`id_sequences` table) ports unchanged.

## Pros and Cons of the Options

### A. Status quo (markdown + text ID conventions)

#### Positive

- Zero tooling overhead
- All content is human-readable and diffable today
- No migration cost

#### Negative

- IDs are unenforced text: broken references are invisible
- No cross-artefact queries without bespoke parsing
- LLM-generated IDs have no collision guarantee across sessions
- Computation (effort estimates, timelines) requires fragile markdown parsing

### B. SaaS project-management tools

#### B1. Linear

#### Positive

- Excellent DX; clean API; epic/issue hierarchy maps well to E-NN / C-N.M.FXX

#### Negative

- Product layer only: no persona, capability-map, bounded-context, or value-stream modeling
- Proprietary; data in Linear's cloud
- No MCP server; agent access requires bespoke Linear API integration per project
- Cannot be self-hosted

#### B2. Jira + Confluence (Atlassian)

#### Positive

- Extremely flexible; mature API

#### Negative

- Heavyweight and expensive for solo use
- No schema-enforced FK relationships between entity types
- No MCP integration; no Python/marimo query layer
- Confluence adds no enforcement over plain markdown

#### B3. Notion

#### Positive

- Relational databases can model many entity types
- Official API available

#### Negative

- Schema is soft: no FK enforcement
- Proprietary; data not locally controlled
- API rate-limited and eventual-consistent; not suitable as a live tool layer
- Not git-friendly

### C. OSS self-hosted tools

#### C1. Plane (OSS Jira alternative)

#### Positive

- Open source; full data ownership

#### Negative

- Requires running a server (Docker)
- Product tracking only: no business architecture layer
- No MCP server; no Python/marimo integration

#### C2. AppFlowy

#### Positive

- Local-first; open format

#### Negative

- Limited relational features; no Python integration

#### C3. Anytype

#### Positive

- Local-first; genuinely relational object model; open format (IPFS)

#### Negative

- Immature; no SQL interface; no MCP server; no marimo integration

### D. Local DuckDB, human-edited via marimo

DuckDB as single source of truth; marimo notebooks provide the data-entry UI.

#### Positive

- Python-native; excellent in marimo
- Full SQL across all entity types
- Zero infrastructure

#### Negative

- Marimo is the write path: agents cannot write to DuckDB directly without a tool layer; every agent session would need to open a notebook
- No MCP interface; does not satisfy the agent-as-primary-user driver
- Binary file; git diffs opaque

### E. Structured YAML source + DuckDB materialized query layer

YAML is the human-editable source of truth; DuckDB is rebuilt from it on demand.

#### Positive

- YAML diffs are human-readable in git
- Python-native; no server

#### Negative

- LLM-generated YAML is non-deterministic: field ordering, optional fields, phrasing vary across sessions, producing noisy git diffs even with no semantic change. This directly breaks the git-readability value proposition.
- No MCP interface; agent must write YAML files directly, re-introducing the non-determinism problem
- Two representations to maintain before a generation pipeline exists

### F. Local MCP server + DuckDB + YAML export

#### Positive

- Deterministic IDs via DB sequences
- FK enforcement at write time
- Agent-native: any MCP-compatible agent calls the same tools
- YAML export without making YAML the source of truth

#### Negative

- MCP server process must be running at agent-session time: extra operational step
- Heavier than a CLI for the MVP use case where Claude Code's Bash tool suffices
- Schema and migration discipline required
- `clew-mcp` package must be developed and maintained

### G. CLI tool (adr-tools style) + DuckDB + YAML export (rejected — see option I)

Identical architecture to the chosen option I, but on DuckDB instead of SQLite.

#### Positive

- All option-I positives apply
- DuckPGQ extension offers a future property-graph view over the same tables (v2 nice-to-have)
- DuckDB VSS extension is in-engine vector search (v2 nice-to-have)
- Pandas/Polars/Arrow zero-copy materialisation is more idiomatic in marimo

#### Negative

- Adds a non-stdlib binary wheel (`duckdb`) to `pip install clew` — Python stdlib already ships `sqlite3`
- Column-store overhead per single-row INSERT with no offsetting analytical-scan benefit at clew's scale (hundreds-to-low-thousands of rows)
- Concurrency relies on an OS file lock wrapper (`flock`) where SQLite's WAL mode handles the single-writer model in-engine
- DuckPGQ and VSS advantages are speculative v2 capabilities; at MVP they pay no rent

### I. CLI tool (adr-tools style) + SQLite + YAML export (chosen)

See Decision Outcome above.

#### Positive

- `sqlite3` ships in the Python stdlib — zero pip dependency for the DB driver, smallest possible install footprint
- Row-store + WAL mode is the canonical fit for OLTP-shaped CRUD: single-row INSERT per CLI command, recursive-CTE reads at small scale
- Single-writer concurrency handled by the engine (`PRAGMA journal_mode = WAL`); no `flock` wrapper required
- Recursive CTEs (since SQLite 3.8.3, 2014) cover the metamodel's bounded ≤5-hop traversal in microseconds
- JSON1 functions (`json_extract`, `json_set`, `->>` operator since 3.38) cover the typed-property-graph schema in [ADR-0003](adr-0003-schema-design-typed-property-graph.md) without modification
- Expression indexes on JSON paths available if a project ever needs them (`CREATE INDEX ix_status ON artefacts(json_extract(properties, '$.status'))`)
- Most battle-tested embedded SQL engine in existence; binary format stability across decades
- Same `crud.py` core can be wrapped in MCP or FastAPI later without rewrite
- YAML export is deterministic (generated from DB, not by LLM)
- Postgres upgrade path (v3) is short: both are relational, share recursive-CTE semantics, share standard SQL surface

#### Negative

- No in-engine property-graph extension; graph queries stay in recursive CTEs (acceptable at metamodel scale)
- No in-engine vector-search by default; `sqlite-vec` is the v2 add-on if/when needed
- DataFrame interop with marimo goes via `pandas.read_sql` rather than zero-copy Arrow (functionally fine; idiomatically less elegant)
- `PRAGMA foreign_keys = ON` must be set per connection (SQLite quirk; the CLI does this in its connection factory)

### H. Graph database (Neo4j / property graph)

A property graph database storing all artefact types as nodes and cross-references as typed edges, queried via Cypher or a similar graph query language.

#### Positive

- Native graph traversal syntax expressive for multi-hop path queries
- Built-in graph algorithms (PageRank, shortest path, betweenness) available via Graph Data Science library
- No explicit JOIN syntax; traversal is implicit in the query

#### Negative

- **Wrong problem domain.** The metamodel has a fixed, typed schema (19 artefact types with known FK relationships). Graph databases win on variable-schema entities, dynamic traversal depth, and pattern discovery — none of which apply here.
- Maximum traversal depth in clew is 5 hops (persona → value stream → FBS functionality → epic → PRD). Standard SQL `WITH RECURSIVE` CTEs (supported by SQLite, Postgres, DuckDB alike) handle this in milliseconds without a graph engine.
- Requires a server process (JVM for Neo4j): conflicts with the local-first, zero-infrastructure constraint stated in Decision Drivers.
- Not Python-native; poor fit with the marimo analysis layer.
- The "semantic layer" benefit cited in Neo4j literature (helping LLMs write better graph queries) is a query-composition concern addressable at the CLI layer without changing the storage tier.
- Schema and migration discipline still required; graph schema evolution is no simpler than relational migration.

## Project layout

The DB file (`docs/clew/clew.db`) is gitignored; the YAML snapshot directory (`docs/clew/snapshot/`) is git-tracked and never edited directly. Snapshot file names and the full CLI command set are specified in the [CLI interface contract](../../architecture/interfaces/cli-clew.md).
